## What the product is

A presentation rehearsal + live-delivery web app for university students and startup founders. Three features:
- **F1** — rehearsal timer (total + per-slide), runs (회차) compared side by side, optional recording with per-slide playback.
- **F2** — compare the written script against the speech-recognition transcript of what was actually said; user picks sentences to apply to the script, creating a new script version.
- **F3** — live script tracking: highlight the current phrase as the speaker talks; optional `자동 넘김` (auto-advance) moves presenter + audience windows to the next slide.

Laptop and iPad (landscape/portrait) only; smartphones are out of scope. No login, no server-side user data.

## Planned architecture (from PRD §1)

- **Next.js App Router + React + TypeScript + CSS Modules, deployed as one Vercel project.** Public pages (`/`, `/guides/presentation-rehearsal`) are statically generated and must be readable with JS disabled. App routes: `/app` (list + editor + in-place rehearsal + run history) and, from stage 4, `/app/audience` (audience window). There is no separate presenter page: the user found leaving the editor tiring, so rehearsal (and later live mode) switches the editor in place, keeping slide/script positions and with 연습 시작 as one round mic button in the editor's bottom-right corner that turns into round 일시정지 · 종료 buttons while rehearsing. App routes get `noindex` but must **not** be blocked in `robots.txt`.
- **Everything runs client-side.** PDF.js renders slides (current + adjacent first). IndexedDB via Dexie.js stores projects, script versions, runs, transcripts and opt-in audio chunks. getUserMedia + MediaRecorder for recording, saved in chunks.
- **Presenter ↔ audience sync** uses `BroadcastChannel` (same origin, same machine), sending session id + slide number only (`src/lib/audience.ts`: `slide` presenter→audience, `hello` audience→presenter on open, `step` ±1 from a key/clicker pressed in the audience window, `bye` when either closes; `readMessage` drops anything else). The audience window must never receive script, transcript, notes or recording state; it reads the PDF from IndexedDB itself. Presenter side: `useAudienceLink` (session id kept in sessionStorage per project so an open audience window reconnects after a reload; it follows `current`, so manual moves and auto-advance both reach it). Audience: `/app/audience?project=<id>&session=<id>` → `src/components/audience/AudienceScreen.tsx` (black, slide centred, one click anywhere or F = full screen (browsers need a click in that window), cursor and hint hide when idle, closes itself on `end`, notes for connecting / presenter closed / PDF missing). **No 연습/실전 split** (the user found it complicated; like PowerPoint's presenter view instead of Canva's two loose windows): one start menu; only when a second display is connected (`screen.isExtended`, Chromium) it shows a `프로젝터에 슬라이드 띄우기` switch (default on, remembered). Starting with it on opens the audience window placed on the projector via the Window Management API (`getScreenDetails` → `pickAudienceScreen` → `window.open` with that screen's box; permission asked when the menu opens, falls back to a normal window), the top bar says `발표 중` and `프로젝터 연결됨 / 프로젝터에 다시 띄우기`, and 종료 sends `end` and **saves no run** (`rehearsal.discard`; the user doesn't want talks kept — revisit when recording exists). Without a projector everything is the plain rehearsal. `Run.mode` stays `"rehearsal"`; old `"live"` runs still show `N회차 실전`.
- **Speech recognition**: Web Speech API with `processLocally = true` only. If on-device recognition isn't available, fall back to "수동 진행" (manual mode) — **never silently fall back to a cloud speech API**. whisper.cpp WASM in a Web Worker is a candidate fallback, lazy-loaded and cached per version.
- PDF engine and speech models must load only when their feature opens (public homepage first load: zero such requests).

## Invariants that span multiple features

These come from PRD §4 and are easy to break:
- **Versioning**: each run records the PDF + script version it started with. Editing the script creates a new version; past runs keep their original script/transcript/audio alignment.
- **Timing (§4.2)**: total = start→end minus explicit pauses only (silence counts). Revisiting a slide accumulates its time; audio is replayable per visit in order. Acceptance T2: 20s on slide 1, 10s pause, 30s slide 2, 5s slide 1 → total 55s, slide 1 25s, slide 2 30s.
- **Recognition and recording are independent toggles.** Timing is always saved; transcript only if recognition is on; raw audio only if `녹음 보관` is on.
- **Matching (§4.3)**: normalize (whitespace, punctuation, case) for comparison only, keep display text unchanged. Compare the current phrase and the next 3; the highlight moves forward only (going back only via a click — the user found back-and-forth jumps distracting). Korean → contiguous character n-grams; English → word overlap + order. Hold position on silence, ambiguous ad-libs, or matches on only a number/common conjunction. Never advance highlight based on elapsed time. Manual slide change discards pending recognition for the previous slide. Auto-advance fires once per slide visit: as soon as the last phrase of the slide has been said to its end (the user wants the next slide up before they speak about it; `advanceAtEnd` in useScriptTracking, 300 ms delay so the star lands), or when the end of the current slide and the start of the next are both confirmed (`startedNextSlide`). The highlight advances per word: once a word has begun it is shown to its end (`wordEnd`), so a differently said ending (어렵습니다 vs 어려워요) doesn't leave the star stuck; a word also counts as begun when the next syllable said shares the script syllable's first consonant (`sameSyllableStart`: 보세요 said as 보겠습니다/볼게요/봐요, 합니다 as 해요, 됩니다 as 돼요); if that begun word is followed by at most one more word and the speaker said 2+ more syllables, the phrase counts as finished (보시기 바랍니다 said as 보세요). Tests in matching.test.ts list the accepted endings. When a phrase that isn't the slide's last is said to its end, the tracker moves to the next phrase at once (`followSpeech` in matching.ts, used by `commit`), so the star goes to wait beside it. **Runaway guard** (a real bug: one sentence skipped several phrases and slides): tracker offsets are positions in `spokenSoFar(finals, interim)` — confirmed text plus the in-progress guess — so "listen from here" also drops words still in progress (they used to be re-matched against each new phrase, and every Korean sentence ends in 니다); `limitToHeard` caps the star at ~1.5 script letters per letter heard (+2); 2–3 letter matches only count within 8 letters of the current spot. Korean sentence endings (`ENDING_KO`: 습니다, 겠습니다, 합니다, 세요, 해요, 도록…) are left out of position evidence — their bigrams are dropped in `phraseScore` and stripped in `isInformative` (content threshold 2 letters) — because the end of the previous slide's sentence ("…소개하도록 하겠습니다") arriving after an auto-advance used to match whichever phrase ended in 있습니다 and skip the first phrase; `phraseTail` reaches back until it holds 2 content bigrams. Tests: "no runaway" and "sentence endings say nothing about position" in matching.test.ts. Dev: `__slidecueSpeak(text, true)` sends text as an in-progress guess.
- **Privacy**: PDF, script, audio and transcripts never leave the browser. File names and script text must not appear in URLs, analytics events or error logs. GA4 events use fixed paths/step names only; `first_rehearsal_completed` fires once after the first run with duration > 0 is persisted. Exclude audience window and preview deployments from analytics.
- **Storage failures**: report which items saved vs. failed; a failed audio save must not lose the script or other runs. Test IndexedDB schema upgrades against existing data before releasing.

## Code layout

- `src/app/` routes; `/app/*` routes are client-heavy and carry `noindex` via `src/app/app/layout.tsx`.
- `src/lib/db.ts` — the single Dexie database. Add tables only by adding a new `db.version(n)` block; never edit an existing version's schema (users' IndexedDB data must upgrade cleanly).
- Script versions: a project points at `currentScriptVersionId`. Unlocked versions are edited in place; once a run uses a version it is `locked`, and the next edit copies it into a new version (`saveSlideScript` in `src/lib/db.ts`).
- `src/lib/pdf.ts` lazy-imports `pdfjs-dist` so the PDF engine only loads on app screens. PDF.js "display" renders wait for animation frames, so they stall in a hidden/background tab; `renderThumbnail` uses the "print" intent to avoid that.
- Live script tracking: `src/lib/matching.ts` (pure phrase matcher per PRD §4.3, tests in `matching.test.ts`), `src/lib/speech.ts` (Web Speech API, **on-device only**: `SpeechRecognition.available/install` with `processLocally: true`; anything unconfirmed → manual mode, never a cloud recognizer), `src/hooks/useScriptTracking.ts` (event-driven: `start` / `changeSlide` / `selectSegment` / `stop` → per-slide transcripts saved on `Run.transcripts`). Meaning matching: `src/workers/embedder.worker.ts` runs `Xenova/multilingual-e5-small` (q8, needs the `query: ` prefix) via `@huggingface/transformers` in a Web Worker; `src/lib/semantic.ts` wraps it (prefetched from the start menu, cached per text). e5 cosines cluster ~0.80–0.95, so `semanticScores` in matching.ts gates at 0.865 and scores by lead over the runner-up — retune those constants if the model changes (paraphrase-multilingual-MiniLM was tried and ranked Korean paraphrases wrong). In dev, `window.__slidecueSpeak("…")` simulates speech, `__slidecueTracking()` shows tracker/meaning state and `__slidecueProbe(text)` returns cosines vs. the current slide (all stripped from production). The browser pane has no on-device Korean model, so test there with a stand-in `window.SpeechRecognition` whose `available()` resolves "available"; real mic checks need desktop Chrome.
- Tracking display: `src/components/editor/TrackedScript.tsx`. Exactly one phrase is tinted (`--highlight-bg`); inside it a #00FCB4 2px line grows from the first character to the spoken one, with a 15px mint asterisk at the head of the line, like a full stop: centred on the line (7px under the text box; phrases use line-height 2.2 so the star clears the ink of both text lines), 3px after the line end (a gap, not touching), so the line reads as its trail. Before a phrase is started the star waits outside the tinted box, on its left at mid height, and slides in over the first character. Motion runs every animation frame (requestAnimationFrame, no CSS transitions or stepping): the star closes the gap in about 0.18 s, never slower than 14 chars/s, so fast speech moves it fast, and snaps onto the goal when within 0.01 char; when speech moves on to the next phrase it first runs to the end of the old phrase, then the emphasis moves at once (clicks switch immediately). It spins one way at 150°/s while moving, easing in and out of the spin. The line has round ends; the star arms stay square (the user asked). The position comes from `spokenCharIndex` (matching.ts) — end of the latest recognized word, monotonic, never ahead of speech. Line and star are an absolutely positioned overlay placed from cached per-character boxes (re-measured on resize), so text never reflows; on a line change the star jumps (no diagonal slide). No "다음" tags or next-phrase boxes — the user found them noisy.
- `src/lib/timing.ts` is the pure timing reducer (start/pause/resume/goto/end) used by the presenter screen; `timing.test.ts` encodes PRD T2. Runs are saved via `saveRun`, which also locks the script version used.
- Screens: `/app` (`EditorApp` → `Library` or `Workspace` with tabs 대본 / 시간 기록 — the run history; PRD calls it 회차 기록). Rehearsal state lives in `src/hooks/useRehearsal.ts` and is rendered inside `Workspace` (clocks replace the info button; scripts go read-only). `?project=<id>&run=<id>` opens a project on its run history. There is one script tab (`대본`); the separate 전체 대본 tab was removed (the user saw no difference from the slide-by-slide view). Before any script exists (and no runs), the tab row shows a `슬라이드별 대본 · 전체 대본` switch instead of the tabs; once a slide has text (or a run exists) it becomes `대본 · 시간 기록` (`showTabs` in Workspace). `전체 대본` shows `WholeScriptPanel`: pasting into the empty box splits at once with `splitWholeScript` (slide numbers, `/` separators, or matching against PDF text), saves, and returns to the slide cards — typed text uses the `슬라이드별로 나누기` button — with a `n장으로 나눴어요 · 되돌리기` bar that restores the previous script. 연습 시작 is a single round mint mic button (`StartRehearsalButton variant="fab"`, icon only, title/aria "연습 시작", menu opens upward right-aligned) in the bottom-right corner of the editor split (`.fab`), always visible except on the 전체 대본 paste screen; while rehearsing it becomes round 일시정지/재개 (white) and 종료 (mint) buttons. The top bar has no rehearsal buttons any more (only clocks, and the save-failure 다시 저장). The user found two 연습 시작 buttons of different sizes odd. The slide viewer shows no focus ring when focused for arrow-key navigation (the user found the green outline distracting). 연습 기록 (`RunsPanel`, tab label changed from 시간 기록) shows the current run on top — `N회차` · date · total (small grey `총 시간` label above; totals are `--primary` deep green, 20px on top and 14px in the list, never big black), then a `⋯` button (`RunActions`: 17px, light `--ink-faint`; it opens a small menu `메모 쓰기/고치기` · `삭제`, each leading to the same small cards — memo editor, delete confirmation.
